## Rules and integration boundaries

[PD-103](../personality-and-trait-rules.md) is rule version 1, not balance proof.
`record_identity_event` is an internal Rust producer boundary, not an arbitrary Tauri incident command.
Media, wellness, sponsor, contract and history systems must supply verified fictional events later;
none are fabricated to populate a demo. No real-person allegations or personality inference are
supported. Manual database/trait editors remain future modding work.

Visibility is public, company-scoped or hidden. Unknown is not average. Policy evidence is counted
separately per company and visibility; unrelated employers' cases never silently combine.
The UI shows the latest 30 transitions; complete events and history stay saved. Normal expiry does
not rewrite past events. Corrections preserve incident identity and visibility. Daily evaluations
increment ledger revisions; producers must reload after stale-write rejection.
Assessment discovery, relationships and profession ratings remain WM-021/023/032.

## Developer learning

**Why derive a personality description instead of storing another editable stat?**
`PersonIdentity::describe` projects validated assessments. Storing assessments and labels separately
would permit contradictions after edits. Stable thresholds and tie order produce repeatable
explanations. Project private inputs out before derivation: hiding only the number afterward could
still leak it through a label.

**Why use both event IDs and revisions?**
`SaveRepository::record_identity_event` accepts an exact repeated ID without a second effect.
A revision rejects different requests based on stale state. An immediate SQLite transaction commits
evidence, states and history together, so a crash cannot save half an update. Neither mechanism
replaces the other. Test successful retries as well as conflicting and stale writes.

**Why not reuse the world generator's random stream?**
Extra draws shift later generated values and potentially match outcomes. An independent seeded
stream creates repeatable identity without perturbing legacy generation. Snapshot hashes change
because the stored shape grows; a separate event hash proves gameplay did not drift. The reusable
strategy is to test behaviour separately from serialized representation.

## Commands used

- `pnpm rust test --workspace`: runs every crate's tests with the repository's Windows toolchain
  wrapper. `-p wm-persistence --test identity` narrows iteration to one integration target. Exit zero
  means all selected assertions passed; failures name the test to inspect. Safe to rerun.
- `pnpm rust fmt --all`: formats Rust workspace code. Safe to rerun but edits formatting; review the
  diff. `pnpm exec prettier --write <paths>` formats only the named web/document files.
- `pnpm check`: formatting, lint, TypeScript, React tests and production web build, in order.
  A failure stops later checks; it does not mean those checks passed. Safe to rerun.
- `pnpm rust clippy --workspace --all-targets`: checks production and test Rust for suspicious
  patterns. Warnings require review even when compilation succeeds. Safe to rerun.
- `pnpm build:desktop:debug` then `pnpm test:desktop`: builds the native application and tests an
  isolated career, profile, booking and restart. Creates artifacts and an owned process, not player saves.

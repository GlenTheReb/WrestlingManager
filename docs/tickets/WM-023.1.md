## Rules and integration boundaries

[PD-104](../relationship-and-interaction-rules.md) is the canonical implemented rule set. Personal
relationships are directional and remain distinct from match chemistry, company sentiment,
contracts and kayfabe. Only tension passively decays; affinity, respect and trust require causal
events. The current player is not yet a persisted Person, so management rapport is a deliberately
separate company-to-worker record until WM-030 introduces roles and authority.

Interactions use a four-point daily attention budget, once-only introductions, per-action cooldowns
and explicit prerequisites. Outcomes contain stored factors plus exact applied relationship, morale
and confidence deltas, with validated prose derived from those values, so replies remain auditable.
Later systems may call the internal personal-event boundary with real fictional events, but there is
no arbitrary UI command for manufacturing relationships. PD-105 is documented design for WM-011;
it is not runtime behaviour. The broader social feed remains WM-036.

## Developer learning

**Why are personal relationships directional?** John can respect Alex while Alex distrusts John.
Storing one shared row would erase that useful asymmetry. The key is `(subject, other)`: every event
states whose viewpoint changes, while a genuinely mutual event can deliberately write both rows.

**Why store a reply and its factors rather than regenerating prose on every view?** The interaction
is a historical fact. Persisting the resolved outcome makes reloads and inbox links stable, supports
auditing and avoids a network or language-model dependency. The reusable principle is to resolve a
command once, then read its immutable result.

**Why combine request IDs with expected revisions?** A repeated request ID safely returns the first
outcome instead of charging attention twice. A revision rejects a different action based on stale
relationship state. Idempotency protects retries; optimistic concurrency protects ordering.

## Commands used

- `pnpm.cmd rust test --workspace` runs all Rust unit and integration tests through the repository's
  Windows toolchain wrapper. A zero exit means every selected assertion passed; safe to rerun.
- `pnpm.cmd check` runs formatting checks, ESLint, strict TypeScript, React tests and the production
  web build. It stops at the first failure, so later stages only count when the command completes.
- `pnpm.cmd rust clippy --workspace --all-targets -- -D warnings` checks production and test targets
  and treats every warning as a failure. It is safe to rerun and does not edit source files.
- `pnpm.cmd build:desktop:debug` embeds the current web build in the native executable;
  `pnpm.cmd test:desktop` then drives an isolated real career without touching player saves.
